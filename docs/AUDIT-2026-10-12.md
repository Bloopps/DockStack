# Audit complet : bugs, sécurité, interface (12 octobre 2026)

Relecture intégrale du code (≈ 14 700 lignes hors tests), puis vérification
de chaque point contre la CLI `docker compose` v5 et contre un **vrai démon
Docker 29.8** (stockage d'images containerd, cgroups v1). Chaque correction
est accompagnée d'un test qui échouait avant elle.

## Résumé

- **Ligne de base rouge** : 7 tests échouaient avant toute modification
  (captures en double sur une machine en UTC, cf. bug 4). La CI tourne en
  UTC : elle aurait échoué de la même façon sur `master`.
- **2 bugs critiques** de perte de données :
  - un `up` ou un Recreate repartait sur des **volumes anonymes vides** ;
  - « docker volume prune » sur un démon ancien effaçait **aussi les volumes
    nommés**.
- **4 bugs importants** :
  - Remove annonçait un succès sur une stack orpheline sans rien supprimer ;
  - captures en double sur une machine en UTC ;
  - `COMPOSE_PROFILES` ignoré ;
  - espace libérable sous-estimé de moitié avec le stockage containerd.
- **2 durcissements de sécurité** :
  - les séquences d'échappement venues de l'extérieur (OSC 52, C1) sont
    retirées partout où ces textes s'affichent ;
  - `↩` ne confirme plus les actions qui effacent des données.
- **15 corrections mineures** d'exactitude et d'interface.
- Petite amélioration : `dockstack --version` et `--help`.

État final : `gofmt`, `go vet` (avec et sans `-tags integration`),
`staticcheck` et `go test -race ./...` passent. Sur le démon réel :

- tous les tests d'intégration de `internal/tui` passent, parcours compris
  (`DOCKSTACK_JOURNEY_DIR=demo-stacks`) ;
- dans `internal/compose`, tous passent sauf `TestLiveLifecycle`, bloqué ici
  par la limite de débit de Docker Hub (voir « Limites »).

## 🔴 Critiques

### 1. Volumes anonymes perdus à chaque recréation

- **Reproduction** : un service dont l'image déclare `VOLUME`, sans volume
  nommé (cas fréquent : une base de données lancée sans `volumes:`). On
  écrit des données, puis Recreate (ou `u` après une mise à jour d'image).
  Le service redémarre **vide**, et l'ancien volume reste orphelin (puis
  proposé à la suppression par la page Nettoyage).
- **Cause** : `CreateOptions.Inherit` restait à `false` (valeur zéro). La CLI
  le met à `true` sauf avec `--renew-anon-volumes`.
- **Correction** : `upOptions` (client.go) construit les options d'`up` et de
  Recreate avec `Inherit: true`.
- **Tests** : `TestUpOptionsInheritAnonymousVolumes` (unitaire) et
  `TestLiveRecreateKeepsAnonymousVolume` (démon réel). Avec l'ancien code,
  `cat /data/f` après Recreate : « No such file or directory ».

### 2. « docker volume prune » efface les volumes nommés sur un démon ancien

- **Reproduction** : démon d'API < 1.42 (Docker 20.10, encore livré par
  Debian 11 et d'anciennes Ubuntu), commande « docker volume prune » de la
  page Nettoyage. Avant la 1.42, `/volumes/prune` sans filtre supprime
  **tous** les volumes inutilisés, nommés compris : les données des stacks
  arrêtées. La page annonçait « Volumes anonymes ». Le client accepte ces
  démons (API minimale 1.40).
- **Correction** : la commande est refusée sous l'API 1.42, avec un message
  qui explique pourquoi, sans appeler le démon.
- **Test** : `TestPruneVolumesOldAPIRefused` (faux démon, client figé en
  1.41). Sans le garde-fou, `/volumes/prune` est bien appelé.

## 🟠 Importants

### 3. Remove « réussi » sur une stack orpheline, sans rien supprimer

- **Reproduction** : conteneur recréé par watchtower (label projet perdu,
  stack marquée ⟳), Remove. Le résultat affiche OK, mais le conteneur tourne
  toujours et son volume reste en place.
- **Correction** : `removeLive` retire d'abord les orphelins du projet, comme
  Down le faisait déjà. La règle de sécurité ne change pas : jamais un
  conteneur rattaché à un autre projet, ni un conteneur lancé hors compose.
- **Test** : `TestLiveRemoveOrphaned` (démon réel).

### 4. Captures d'état en double sur une machine en UTC

- **Reproduction** : fuseau local UTC (la plupart des serveurs, la CI), une
  capture. La liste en montre deux : la capture et le fichier texte
  `active_stacks`, censé être écarté comme doublon.
- **Cause** : dédoublonnage par `map[time.Time]`. La date relue du JSON est
  en UTC et celle du texte en heure locale : même instant, mais `Location`
  différente, donc deux clés distinctes.
- **Correction** : clé en secondes Unix.
- **Tests** : `TestListNoDuplicateLocalUTC` (échoue même sous `TZ=Europe/Paris`
  avec l'ancien code), plus les 7 tests qui étaient rouges.

### 5. `COMPOSE_PROFILES` ignoré

- **Reproduction** : `COMPOSE_PROFILES=debug` dans le `.env`. La CLI active
  les services du profil, dockstack ne les voyait pas : `up` ne les
  démarrait pas et le mode services ne les proposait pas.
- **Correction** : les profils sont lus comme `cli.WithDefaultProfiles` (le
  process l'emporte sur le `.env`). La page Nettoyage reconnaît aussi les
  images des profils inactifs comme citées par une stack. Le cache des
  services déclarés suit désormais le `.env` et l'override, pas seulement le
  fichier compose.
- **Tests** : `TestLoadProjectComposeProfiles`, `TestCollectStackRefs`
  (profil inactif), `TestDeclaredServicesFollowDotEnv`.

### 6. Espace libérable faux avec le stockage containerd

- **Constat** : avec le stockage d'images containerd (défaut des
  installations neuves de Docker 29), la taille d'une image comprend les
  couches décompressées **et** les blobs compressés. Le calcul couche par
  couche ne comptait que la première part, et l'annonçait exact.

  | | Prévu (avant) | Prévu (après) | Libéré réellement |
  |---|---|---|---|
  | 3 images jetables | 11,5 Mo (« exact ») | 21,2 Mo (≈) | 23,1 Mo |

- **Correction** : la part compressée est estimée au taux de compression
  moyen des images supprimées, et le chiffre est marqué « ≈ ». L'API n'expose
  pas la taille de chaque blob, donc l'exactitude n'est pas atteignable ici.
  Le stockage classique (overlay2) garde un calcul exact, protégé par une
  marge de 2 %.
- **Tests** : `TestLayerIndexContentStore`, `TestLiveLayersFreedExact` (égalité
  en stockage classique, ±15 % en containerd), `TestLiveUsageImagesExact`.

## 🟡 Sécurité

### 7. Séquences d'échappement venues de l'extérieur

Les logs étaient filtrés, mais seulement des séquences CSI et des contrôles
C0. Trois trous :

- **OSC** (`ESC ] … BEL`) : titre de fenêtre, liens, et surtout **OSC 52**,
  qui écrit dans le presse-papiers du poste. Seul l'`ESC` était retiré et le
  reste s'affichait.
- **C1** (U+0080 à U+009F) : certains terminaux lisent U+009B comme un CSI,
  sans caractère d'échappement.
- **Textes non filtrés du tout** :
  - messages de progression et d'erreur (parfois relayés d'un registre) ;
  - étiquettes d'images de la page Nettoyage (écrites par l'auteur de
    l'image) ;
  - noms de dossiers du sélecteur `o` (n'importe qui peut créer un dossier
    au nom piégé dans `/tmp`) ;
  - erreurs du loader dans la vue compose.

Correction : expression régulière CSI + OSC + séquences à deux caractères,
`unicode.IsControl` pour les contrôles, et `sanitizeText` (une ligne, sans
allocation pour l'ASCII) appliqué à ces textes.

Tests : `TestSanitizeLogLine` (cas OSC/C1 ajoutés), `TestSanitizeText`,
`TestClassifyImageLabelSanitized`.

### 8. `↩` confirmait les actions destructrices

Le panneau d'actions s'ouvre avec `↩` et lance l'entrée choisie avec `↩`.
Sur « Remove », la confirmation acceptait aussi `↩` : un double appui
supprimait les volumes d'une stack. Désormais :

- Remove, un nettoyage qui inclut des volumes, et les commandes prune qui
  effacent des données (`volume prune`, `container prune`, `system prune`)
  ne se confirment qu'avec `y` ;
- `↩` affiche un rappel ;
- les autres confirmations gardent `↩`.

Tests : `TestRemoveNeedsExplicitY`, `TestPlainConfirmKeepsEnter`,
`TestCleanupVolumesNeedY`, `TestPruneErases`.

## Améliorations

- `dockstack --version` : la version injectée par GoReleaser (ldflags par
  défaut), sinon celle du module (`go install …@vX`), sinon la révision VCS.
  `--help` résume l'usage ; un argument inconnu est refusé (code 2) au lieu
  d'être ignoré.
- README : page Nettoyage (`n`) documentée (elle n'y figurait pas), parité
  CLI (`.env`, override, `COMPOSE_PROJECT_NAME`, `COMPOSE_PROFILES`, volumes
  anonymes), confirmation par `y`, `--version`.

## Limites et pistes

- **govulncheck** n'a pas pu être lancé ici (vuln.go.dev bloqué par le
  réseau) ; le job CI le lance.
- **golangci-lint** : la version disponible est compilée avec Go 1.25 et
  refuse un module en Go 1.26. C'est aussi pourquoi le job CI est non
  bloquant. À rendre bloquant dès qu'une version compilée avec Go ≥ 1.26 est
  épinglée.
- **CI** : elle ne tourne que sur `master` ; une branche de travail n'est
  testée qu'à l'ouverture de la PR. Le bug 4 montre l'intérêt d'un `push`
  sur toutes les branches.
- **Noms de stacks** (dossiers du dossier de stacks) non assainis à
  l'affichage. Ce sont les dossiers de l'utilisateur, le risque est faible.
- **Tests d'intégration propres à l'environnement** :
  - `TestLiveLifecycle` a échoué ici sur la limite de débit de Docker Hub
    (HTTP 429), sans rapport avec le code ;
  - `TestLiveUsage` supposait au moins un conteneur sur la machine, rendu
    indépendant de ça.
